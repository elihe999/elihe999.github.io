我的 SDD 笔记整理：规格、门禁，以及凭什么说做完了#

翻了一遍仓库里跟规范驱动开发有关的笔记：Spec/ 六篇、模板/ 里三个版本的 ADR、AI开发流程/ 的测试与 OpenAPI，加上散在 AI/ 里的上下文和多代理记录。它们记的时间点不同、粒度也不同，但串起来读，其实只在回答三个问题。

一、规格真正值钱的是两个字段#

[[基本流程]] 里列了 spec 该有的六项：Problem Statement、Success Metrics、User Stories、Acceptance Criteria、Constraints，外加 Goals / Non-Goals。同一篇里还有一段登录功能的例子，需求写成 SHALL rate-limit to 5 attempts per 15 minutes，场景写到"第 6 次失败 → 提示限流"，约束写到"不得暴露邮箱是否存在"。

这些字段我一开始当成格式要求，后来发现真正起作用的是其中两个。Non-goals 挡的是 AI 的静默假设和过度工程——超出范围的猜想不再由它自行决定；可观察的验收标准挡的是"应该没问题了"。[[constitution]] 的四条原则里就有一句"验收标准必须可观察"，而 [[基本流程]] 在 Success Metrics 后面直接标了"必须可量化"。写不出可验证条款的时候，通常不是模型的问题，是我自己没想清楚。

顺带一提，[[基本流程]] 的 Feature Spec 模板还留了一格边界条件矩阵：空值缺省、重复幂等、并发竞态、权限可见性。这四格是我漏得最多的地方。

二、一次变更不是一个文件，是五件套#

[[基本流程]] 里那个 docs/specs/checkout-coupon/ 目录我抄下来了：proposal.md（为什么现在做、影响谁）、spec.md（需求和场景）、design.md（决策和取舍）、tasks.md（可评审的实现切片）、test-evidence.md（合并前必须提供的证据）。

入口是 [[Spec/spec|spec.md]] 那份提案模板，带 Draft / Review / Approved 状态机；末尾有一栏 Evidence Required——测试、日志或指标、手工核对、回滚信号，四种证据在开工前就得声明，不是事后补。

不同工种的规格另有模板：[[db-spec-template]] 要求写迁移步骤、回填策略、回滚方案，还有一栏读写兼容窗口；API 模板要求写向后兼容说明和废弃策略。取舍记录用 ADR，[[ADR|模板目录]] 里存了三种版本：最简的 Nygard（状态 / 背景 / 决定 / 后果）、MADR 完整版（多了决策者、驱动因素、候选方案）、以及我自己那份五行版。MADR 里有条提示值得记住：候选方案不要遗漏最终被否决的选项——被排除的路径正是后人不重复踩坑的原因。

三、AI 的编码纪律和流程是互补的#

[[Karpathy Guidelines：LLM 编码行为四大原则|Karpathy 四大原则]] 那篇我留在 Spec/ 里，因为它给出了一个映射：Think Before Coding 由 Specify 阶段的消歧与 Out-of-Scope 承担；Simplicity First 由 Plan + Tasks 的原子化切片承担；Surgical Changes 由"每次只执行一个 Task"加 PostToolUse 检查承担；Goal-Driven Execution 由验收标准加 TDD 的 RED→GREEN 循环承担。结论就一句：SDD 在流程层面解决了 Karpathy 在行为层面指出的问题。

[[AI/Harness]] 那篇补上另一半——光有约定不够，得有机械强制。护栏分三层：权限（默认不能删库、推远程、发消息）、策略（AGENTS.md / constitution 写清禁区）、人审（危险步骤必须点头）。[[多代理]] 里记的三角色流水线也落在这上面：调研代理只读、实现代理按 spec 改代码并跑测试、审查代理对照 spec 挑问题，人只在"接受计划"和"合并"两关拍板。

四、凭什么算完成：证据，不是自述#

[[coding-review]] 那份检查表是整套东西的收口：先做范围核查（允许改哪些文件、实际改了什么、有没有越界），再做规格一致性（验收标准满足没有、有没有 spec 之外的新增行为），最后才是证据（加了什么测试、命令是什么、日志或截图）。

[[AI/Harness]] 把这个循环叫评价回路：好回路靠可自动跑的检查，坏回路是"代理说完成了"就算完。[[上下文工程]] 里那张"该记 / 不该记"表是同一个意思——已确认的 Spec 与 ADR 才进长期记忆，未验证的假设不记。

还缺的两块#

按 [[SDD 知识点地图]] 的统计，缺口集中在两处：Verify 之后的规格回写与归档（现在只有提案的入口，没有闭环），以及度量——返工率、澄清轮次、越界变更率、spec 场景覆盖率，一个都没定。前一个是流程断点，后一个决定这套东西到底有没有让事情变好。

如果你也在攒这类模板，我的建议是从最轻的三样开始：一份 constitution、一张提案模板、一份合并前的 review 检查表。剩下的，等你第一次被 AI"顺手改多了"坑到之后再补也来得及。
